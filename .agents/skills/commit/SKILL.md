# Commit

변경 의도와 범위를 확인하고, 사용자가 승인한 변경만 로컬 Git 커밋으로 저장한다.

## 절차

1. **변경사항 분석**
   - 적용되는 AGENTS.md와 저장소의 커밋 규칙을 확인한다.
   - `git status --short`, `git diff --stat`, `git diff`, `git diff --cached`로 미스테이징·스테이징 변경을 모두 분석한다. 추적되지 않은 파일은 별도로 내용을 확인한다.
   - Git 저장소가 아니면 원인을 알리고 중단한다. 임의로 `git init`하지 않는다. 변경이 없으면 커밋하지 않고 알린다.
   - `.env` 파일과 API 키·비밀번호 등 민감한 정보는 커밋에서 제외한다. 비밀값을 응답이나 커밋 메시지에 노출하지 않는다.

2. **논리적 단위로 분류**
   - 파일 수가 아니라 변경 목적과 의존성을 기준으로 묶는다. 독립적인 기능 추가, 버그 수정, 리팩터링, 유지보수는 별도 커밋으로 제안한다.
   - 사용자가 지정한 범위를 우선하고, 관련 없는 기존 변경은 포함하지 않는다. 기존 스테이징 상태를 임의로 해제하거나 변경사항을 버리지 않는다.
   - 프로젝트에 정의된 린트 검사를 실행하고 통과 여부를 확인한다. 변경에 필요한 테스트·빌드가 있으면 함께 확인한다. 검사 실패 시 커밋을 중단하고 원인을 알린다. 검사 명령이 없거나 실행할 수 없으면 승인 요청에 그 한계를 명시한다.

3. **한국어 커밋 메시지 작성**
   - 제목은 `feat: 요약`, `fix: 요약`, `refactor: 요약`, `chore: 요약` 중 실제 변경에 맞는 형식을 사용한다. 요약은 한국어로 간결하게 작성한다.
   - `feat`는 기능 추가, `fix`는 오류 수정, `refactor`는 동작을 유지하는 구조 개선, `chore`는 설정·문서 등 유지보수에 사용한다.
   - 예: `feat: 컴포넌트 생성 화면에 레트로 테마 적용`
   - 필요한 경우 본문에 변경 이유와 주요 영향을 한국어로 설명한다.

4. **승인 후 커밋**
   - 커밋별 포함 파일·변경 요약·정확한 메시지·검사 결과를 먼저 보여주고 사용자 승인을 요청한다. 이 스킬의 "사용자 승인 후 커밋" 절차에 따른 요청임을 설명한다.
   - 일반적인 "커밋해줘" 요청만으로 제안한 파일과 메시지까지 승인된 것으로 간주하지 않는다. 구체적인 제안에 대한 명시적 승인을 기다린다.
   - 승인 후 diff를 다시 확인한다. 승인한 범위나 메시지가 달라져야 하면 변경된 제안을 보여주고 다시 승인받는다.
   - 승인된 파일 또는 변경 구간만 명시적으로 스테이징하고 `git diff --cached`로 실제 커밋 대상을 확인한다. `git add .`로 관련 없는 변경을 함께 포함하지 않는다. 기존 스테이징과 분리할 수 없으면 상태를 보존하고 사용자에게 알린다.
   - 승인된 순서와 메시지로 `git commit`을 실행한다. 훅이나 커밋이 실패하면 원인을 알리고 중단하며 `--no-verify`로 우회하지 않는다.
   - `git log -1 --format="%h %s"`와 `git status --short`로 결과를 확인하고 커밋 해시·메시지·남은 변경을 보고한다.
   - 별도 요청 없이 push, amend, reset 또는 이력 재작성을 수행하지 않는다.
